# Phase 1 MVP — implementation plan

Status: drafted 2026-04-23 against [docs/specs/2026-04-23-phase-1-mvp-design.md](../specs/2026-04-23-phase-1-mvp-design.md).

This plan decomposes the MVP into nine independent concerns. Each concern ships on its own branch, its own PR, and its own local-test cycle — there is no umbrella branch. Concerns are ordered topologically; the dependency graph is in [`concerns.json`](./2026-04-23-phase-1-mvp-concerns.json).

---

## Ground rules

- **Test-driven development inside each concern.** Every task that produces code writes its failing test first, then makes it pass. Concerns that produce only configuration / scripts / infrastructure (foundation, deploy-stack, agent-install, docs-polish) use acceptance-check-first discipline instead: write a command or script that fails against the missing state, then add the files that make it pass.
- **File ownership is strict.** No two concerns modify the same file. If a need arises, the work must be split into a prerequisite concern that owns that file.
- **No CI in this repo.** Tests run locally only: `pnpm -C app test`. Acceptance = the command exits 0 and implementation matches spec. Decisions doc defers GitHub Actions to a later phase.
- **Default branch is `main`.** Every PR targets `main`. There is no long-lived feature branch.
- **Package manager is pnpm.** Declared in `app/package.json` via the `packageManager` field.
- **All dependencies declared upfront in foundation.** Downstream concerns never run `pnpm add` — they only `import` from already-declared packages. This is what prevents later concerns from colliding on `package.json` / `pnpm-lock.yaml`.

## 1. `foundation` — scaffold that every other concern builds on

**Branch:** `feat/phase-1-mvp-foundation`
**Depends on:** nothing.

**Why this comes first:** every later concern imports from `$lib/...`, runs under Vitest, or is typechecked against `tsconfig.json`. If foundation doesn't land first, downstream branches can't even install dependencies. All deps are declared here so nobody else needs to touch `package.json` / `pnpm-lock.yaml`.

**Files this concern owns (final list):**

- `app/package.json` — declares every dep the feature needs: `svelte`, `@sveltejs/kit`, `@sveltejs/adapter-node`, `@sveltejs/vite-plugin-svelte`, `vite`, `typescript`, `tsx`, `vitest`, `@vitest/ui`, `jsdom`, `@testing-library/svelte`, `@testing-library/jest-dom`, `pocketbase`, `uplot`, plus typings. `packageManager` pinned to a recent pnpm.
- `app/pnpm-lock.yaml` — generated by `pnpm install` and committed.
- `app/tsconfig.json` — strict mode, `moduleResolution: "bundler"`, path alias `$lib → ./src/lib`.
- `app/svelte.config.js` — `@sveltejs/adapter-node`, preprocess defaults.
- `app/vite.config.ts` — wires the svelte plugin plus Vitest config (jsdom, setup file path reserved for later concerns if needed).
- `app/vitest.config.ts` — separate vitest config if kept out of vite.config.ts.
- `app/src/app.html` — `<html data-theme="…">` skeleton with a `<meta>` tag preloading Roboto Mono. The font preload paths reference `/fonts/RobotoMono-Regular.woff2` etc. — files that design-system will create. The preload is harmless before those files exist (browser logs a 404, nothing more), so it's safe to declare here.
- `app/src/app.d.ts` — standard SvelteKit ambient types.
- `app/.gitignore` — `node_modules`, `.svelte-kit`, `build`, coverage.
- `app/.npmrc` — `engine-strict=true`, `auto-install-peers=true`.
- Root `.gitignore` — already exists; append any repo-wide ignores (e.g. `.env`).

**Explicitly NOT created here:** no `src/lib/*/index.ts` placeholders, no `src/routes/` tree. Downstream concerns own those directories entirely.

**Tasks (TDD discipline = acceptance-script-first for pure scaffolding):**

- **t1 — smoke test first.** Add `app/src/lib/smoke.test.ts` containing `test("vitest works", () => { expect(1 + 1).toBe(2); });`. Confirm `pnpm -C app test` fails with "missing package.json" or similar.
- **t2 — write `app/package.json`** with all deps listed above and scripts: `dev`, `build`, `preview`, `test`, `test:watch`, `check` (svelte-check), `capture-fixtures` (points at a file that will be created later — stub for now). Run `pnpm install`; lock file is committed.
- **t3 — write `app/tsconfig.json`, `app/svelte.config.js`, `app/vite.config.ts`, `app/vitest.config.ts`.** Confirm `pnpm -C app test` now passes (smoke test runs).
- **t4 — write `app/src/app.html` and `app/src/app.d.ts`.** Confirm `pnpm -C app check` passes (typecheck clean on an empty-ish project).
- **t5 — write `app/.gitignore` and `app/.npmrc`. Update root `.gitignore`.** Confirm `node_modules/` is ignored.
- **t6 — delete the smoke test** (it lived in `src/lib/` which is owned by foundation for this one file only; remove it so downstream concerns don't inherit an odd file). Actually: keep it at `app/tests/smoke.test.ts` or `app/src/smoke.test.ts` (top-level `src/`) rather than inside a lib module — that keeps foundation from polluting any module folder. Prefer `app/src/smoke.test.ts` since it verifies the whole pipeline.

**Acceptance:** `pnpm -C app install && pnpm -C app test && pnpm -C app check` all exit 0. No files created outside this concern's owned list. PR title: `chore(foundation): scaffold SvelteKit app and repo-wide ignores`.

## 2. `design-system` — tokens, fonts, theme store

**Branch:** `feat/phase-1-mvp-design-system`
**Depends on:** `foundation`.

**Why it's independent of everything else:** nothing under `lib/design/` imports from `lib/format`, `lib/chart`, `lib/beszel`, or `lib/panels`. It's a self-contained visual layer.

**Files this concern owns:**

- `app/src/lib/design/tokens.css` — CSS custom properties for the two surfaces (`--bg`, `--sub-alt`), three text weights, accent, focus-ring. Dark and light palettes gated by `[data-theme="dark"]` / `[data-theme="light"]`. Motion tokens (125ms ease-out default, 400ms spring, 1.2s pulse).
- `app/src/lib/design/fonts.css` — `@font-face` declarations pointing at `/fonts/RobotoMono-*.woff2`. Weights covered: 400, 500, 700. Tabular-figures font-feature-settings.
- `app/src/lib/design/theme.ts` — Svelte store. On first load reads `localStorage.getItem("theme")`; if absent, falls back to `prefers-color-scheme`. Writes `data-theme` on `document.documentElement` and persists on change.
- `app/src/lib/design/theme.test.ts` — unit tests covering: default is `prefers-color-scheme` when storage empty; explicit `setTheme("light")` persists and sets attribute; reading back returns the persisted value.
- `app/src/lib/design/index.ts` — re-exports `theme` and `setTheme` from `theme.ts`, plus exports that ensure CSS is bundled (`import "./tokens.css"; import "./fonts.css";`).
- `app/static/fonts/RobotoMono-Regular.woff2`, `RobotoMono-Medium.woff2`, `RobotoMono-Bold.woff2` — self-hosted from the Roboto Mono project at a pinned version. The executor resolves the exact source (GitHub release asset) at implementation time.

**Tasks:**

- **t1 — write `theme.test.ts` first.** Three failing tests: default-from-media-query, set-and-persist, round-trip.
- **t2 — implement `theme.ts`.** A `writable`-like store wrapping localStorage + `matchMedia`. Tests pass.
- **t3 — write `tokens.css`** per the spec's design-system section. No visual test; lint via `svelte-check` (css-in-svelte is separate; this is a plain `.css` file).
- **t4 — write `fonts.css`.** Declares the three weights.
- **t5 — drop the three woff2 files into `app/static/fonts/`.** Verify their existence from a simple node script or just `ls`; no unit test for binary assets.
- **t6 — write `index.ts`** re-exporting the store and importing the two CSS files so any consumer that does `import "$lib/design"` gets the bundle.

**Acceptance:** `pnpm -C app test` passes (theme tests green). Visual verification happens later in panels-and-routes. PR title: `feat(design): AbstractNucleus tokens, Roboto Mono, theme store`.

## 3. `format-utils` — numbers, bytes, time

**Branch:** `feat/phase-1-mvp-format-utils`
**Depends on:** `foundation`.

**Why it's independent:** pure functions, no other-module imports.

**Files this concern owns:**

- `app/src/lib/format/index.ts` — re-exports from the files below.
- `app/src/lib/format/number.ts` + `number.test.ts` — `formatThousands(n)` uses U+2009 thin space (`"128 430"`). `formatPercent(n, decimals)` with tabular figures assumption. `formatTabular(n, { decimals })` generic helper.
- `app/src/lib/format/bytes.ts` + `bytes.test.ts` — `formatByteRate(bytesPerSec)` rounds to KB/s, MB/s, GB/s without K/M/B on regular counts (spec says no K/M/B suffixes for plain numbers — but byte rates need unit labels; spec gives `bytes/sec` without shortening per spec fleet table). Clarify: the spec demands no K/M/B on integer counts (RAM free, etc.), but byte *rates* still need units. Executor writes tests that lock the chosen convention: `formatByteRate(1234567)` → `"1.23 MB/s"` (decimals where they matter).
- `app/src/lib/format/time.ts` + `time.test.ts` — `formatRelativeTime(ms)` ("3s ago", "2m ago", "14h ago"). `formatUptime(seconds)` ("14d 03h"). Time math is pure; no Date.now patching needed in tests — callers pass `now`.

**Tasks:**

- **t1 — tests first for `formatThousands`.** Covers: 0, 9, 999, 1 000, 128 430, negative, non-integer. Uses U+2009 exact character.
- **t2 — implement `formatThousands`.**
- **t3 — tests + impl for `formatPercent`, `formatTabular`.**
- **t4 — tests + impl for `formatByteRate`.** Locks unit thresholds and decimal rules.
- **t5 — tests + impl for `formatRelativeTime`.** Injects `now` for determinism.
- **t6 — tests + impl for `formatUptime`.**
- **t7 — write `index.ts`** barrel re-exporting everything.

**Acceptance:** `pnpm -C app test` passes; these functions are consumed later by panels. PR title: `feat(format): tabular numbers, byte rates, relative time`.

## 4. `chart-wrapper` — uPlot wrapper + tween + time-range math

**Branch:** `feat/phase-1-mvp-chart-wrapper`
**Depends on:** `foundation`.

**Why it's independent of format/beszel:** the chart module exposes a Svelte component that takes plain `{ts: number[], values: number[]}` arrays. Formatting axis labels is a consumer concern (panels pass a `formatTick` callback). Time-range math (e.g. "24 h window" → `{startMs, endMs, bucketMs}`) is a pure utility.

**Files this concern owns:**

- `app/src/lib/chart/TimeSeries.svelte` — the uPlot wrapper component. Accepts `data`, `series`, `formatX`, `formatY`, `height`. Manages uPlot instance lifecycle (create on mount, destroy on destroy, `setData` on data change).
- `app/src/lib/chart/tween.ts` + `tween.test.ts` — `tweenNumber(from, to, duration=400, easing=spring)` returns a readable store emitting intermediate values. Used for readouts ("42 %" animating to "47 %").
- `app/src/lib/chart/timeRange.ts` + `timeRange.test.ts` — `timeRangeWindow(label, now)` where `label ∈ "1h"|"24h"|"7d"|"30d"`; returns `{startMs, endMs, bucketMs}`. Bucket sizes chosen to keep <= N points per panel.
- `app/src/lib/chart/TimeSeries.test.ts` — mocks `uplot` via `vi.mock`, asserts constructor is called with an `opts` object containing expected `series` and that `setData` is called on data prop change.
- `app/src/lib/chart/index.ts` — barrel.

**Tasks:**

- **t1 — `timeRange.test.ts` first.** Cases: "1h" yields 1h span, "7d" yields 7d span, bucket sizes monotonic.
- **t2 — implement `timeRange.ts`.**
- **t3 — `tween.test.ts` first.** Checks monotonic approach from `from` to `to`, reaches `to` exactly at `duration`.
- **t4 — implement `tween.ts`.** Simple `requestAnimationFrame` loop with a spring easing. (jsdom needs a polyfill; set one up in a shared test-setup file owned by this concern: `app/src/lib/chart/test-setup.ts`. Register it in vitest config via a module-scoped `setupFiles` entry that `vite.config.ts` references — but foundation owns vite.config.ts. Instead, the test imports the polyfill directly. Keeps ownership clean.)
- **t5 — `TimeSeries.test.ts` first** with `vi.mock("uplot", …)`.
- **t6 — implement `TimeSeries.svelte`.**
- **t7 — write `index.ts` barrel.**

**Acceptance:** `pnpm -C app test` passes. PR title: `feat(chart): uPlot wrapper, tween utility, time-range math`.

## 8. `agent-install` — one-liner install scripts

**Branch:** `feat/phase-1-mvp-agent-install`
**Depends on:** nothing (fully independent).

**Why independent:** these scripts run on agent hosts; they don't import or reference anything in the repo. They only encode the Beszel agent install flow.

**Files this concern owns:**

- `deploy/agent-install/linux-systemd.sh` — Bash. Parses `--hub` and `--key`; detects arch (`uname -m` → `amd64`/`arm64`); downloads pinned Beszel agent release; installs to `/usr/local/bin/beszel-agent`; writes systemd unit; enables + starts; prints status hint.
- `deploy/agent-install/windows-install.ps1` — PowerShell. Parses `--hub` and `--key`; downloads Windows binary; installs to `C:\Program Files\Beszel\beszel-agent.exe`; registers as a Windows service (`sc.exe` per Beszel's pinned-version instructions); starts.

**Tasks:**

- **t1 — write `linux-systemd.sh`.** Test by running `bash -n deploy/agent-install/linux-systemd.sh` (syntax) and by doing a dry-run (`--help` exits 0). No unit-test framework for shell in this project; the acceptance is manual execution on a test VM if the executor has one, otherwise syntax + argument-parsing verification.
- **t2 — write `windows-install.ps1`.** Test by running `pwsh -NoProfile -NonInteractive -Command "Test-ScriptFileInfo deploy/agent-install/windows-install.ps1"` for syntax, or `pwsh -NoProfile -Command "& { . ./deploy/agent-install/windows-install.ps1 -DryRun }"` if a dry-run flag is added.
- **t3 — pin Beszel version** in both scripts via a single top-of-script variable. Same pin as `deploy/.env.example`; the executor verifies the values match during PR review, but no automated cross-check.

**Acceptance:** both scripts pass syntax checks. Executor does NOT need to run them against real hosts during the PR — the spec defers that to post-merge manual verification. PR title: `feat(agent-install): linux-systemd and windows one-liner scripts`.
